## 2. 冻结的 Record 与定位合同

`type=record` 包含 `record_type`、`record_key`、`schema_version`、类型化 JSON `data`、
可空 `detail_url`、每个 data 字段的 locator、`key_locator`、主 snapshot/observation、
补充输入，以及非 URL 业务键需要的 `frozen_parent_request={url,role,method:GET}`。
JSON 有展示 detail_url 时仍冻结父 API；旧行仅从已接受的原文输入恢复唯一父请求。
身份为 `(source_id, namespace, record_type, record_key)`；禁止列表下标或位置哈希作为键。
URL 键必须与实际归档响应及详情 URL 一致；JSON 整数键仅允许显式 `key_string` 转换。

一个响应可输出 0..N Record；一 Record 可引用多个输入，同一 snapshot 可被多个 Record
共享。每字段值必须从已归档输入复算，不接纳脱离原文的替代值。
JSON Pointer 保持数字、布尔、null、数组及对象类型，严格区别 false/0 和整数/浮点数，
拒绝非法转义、负数组下标、NaN/Infinity 和过深 JSON；旧字符串 locator 不变。
`record.v1` 是技术 JSON 合同，`schema_version` 为来源输出版本标识，不意味着业务准确性审核。

内容指纹只取 Record 类型、Schema 版本和有效 data；输入、页码、locator 位置、抓取时间
不进入业务指纹。列表重排只改变原文/定位证据，不改变各业务版本。
同一 Binding 的有效基线负责内容变化归因；换 Binding 的不同输出记为 reprocessed，
不能由新结果推断来源更新。原文 bytes hash 与业务内容变化分别记录。

stage 只写不可变处理结果与 emission；完成事务按键聚合。同键同内容去重并合并所有
输入血缘；同键异内容保留候选，整个键排除有效输出并使本轮 partial。
只有最终 complete 的完成事务推进 Record 当前指针；失败或 partial 不覆盖此前成功视图。
未观察旧 Record 一律 unknown，不自动删除，包括本轮零结果或声明范围不完整的情况。
写入继续遵守 Source → Run → Record 锁顺序及 generation/run_seq/attempt fencing。

## 3. Discovery、分页和资源边界

使用 Scrapy `request_scheduled` 信号在 Scheduler/原生 Dupefilter 之前记录发现，覆盖初始
种子及后续请求，保存实际 RequestFingerprinter 指纹、角色、父 URL/原文/Observation。
原生 `request_dropped` 标记去重；多个父页面可关联同一指纹，Discovery 不调度任何请求。
分页循环由原生去重终止，Recipe 仍可诊断不明确的分页或模板。

下载 Guard、归档、callback 和 item 校验关联 requested、archived、parsed、failed、skipped；
越界、预算、截止、下载失败、解析失败与去重分开计数。重试/跳转保留 transport 关系，
不能把已恢复的临时失败误判为未采资源。证据事件按 attempt 有上限；超过上限明确 partial。
发现数、实际网络交换、归档数、解析数、有效 Record 数分别报告，不据此宣称全站覆盖。

仍只允许冻结 GET/HEAD、无请求体，保留地址、敏感 URL/headers/body、响应大小及预算限制。
`host_path_scopes` 将每个主机与各自允许路径绑定；跨主机附件必须显式声明该映射，
不能扩大为多个主机共享路径的并集。静态 iframe 只跟进同主机公开 GET 子页。
普通展示资源不采集。业务 PDF/TXT/CSV/XLS 和 DOCX 普通段落／表格可归档及定位；
DOCX 未解析对象与无文本层 PDF 保留归档、错误和未知范围，能力边界见第 10 节。
不引入 OCR 或浏览器。

## 4. Recipe、Recheck、Manifest 与查询

共享 helper 为普通 Python：HTML 正文、表格逐行、嵌套 JSON 列表、父来源 Request、
静态 iframe/附件、文本 PDF、XLS 工作表与 DOCX 段落／表格。不同 HTML 结构由 selector 参数或源级 Python 控制；
不引入 DSL、Registry、新 Frontier、消息队列、爬虫框架或工作流引擎。
既有 generic Recipe 和 Candidate 继续可用。

在线 Run Mode 只有 collect/recheck；Replay 仍为归档离线模式。
Recheck 仅对 response_url 身份使用详情 URL；稳定业务键使用冻结父列表/API 请求，
相同父请求仅生成一个种子。调度按到期记录和请求预算冻结本轮目标，完成后才推进检查日期；
请求内部仍由 Scrapy 原生去重。周期任务的到期查询也包含 Record，Procrastinate 继续
负责持久调度。旧 V1.1 文档 Recheck 路径保留。

完成报告引用内容寻址、版本化 Manifest Artifact，包含研究 ID、Source、Binding、
RecipeVersion、Run、业务 scope、结果引用和资源统计。研究 ID 来自冻结配置，
不等同于 Source ID，不创建第二份人工状态表。`inspect research/source/run/manifest`
及 Export 可回查机器事实；Export 保留 documents，增量增加 records。
显式 Run 包括 partial 中有效输出；默认视图只选最近 complete 的成功输出，
已消失或未观察数据不自动抹除。所有出口 `quality_status=not_evaluated`。

## 9. Recheck 与 JSON 规模修正

本节为上一轮修复（`8ac05fe`）的冻结结果；“当前”指该轮引擎。最新引擎复验见第 10 节。

用户提出三项 P1 和一项 P2，先冻结本节失败合同，再添加真实 CLI/Scrapy/隔离
PostgreSQL 行为验收，观察现有失败后修正实现。仍使用同一个 Plan 与 Generated，
先前第 8 节原文与版本证据保持不变；引擎变更后重新 pack/Binding，不将旧工件
声称为新版本已经验收。

业务边界：Record 身份来源于稳定业务键，展示用 detail_url 不赋予另一种身份；
调度按到期范围组织有限请求，采集与 Replay 继续共享原文定位合同。JSON 对象的
解析复用只存在于单个验证/Crawl 的有界生命周期内，数据边界仍是已校验摘要的
不可变原文；具体 API 分页保留在来源 Recipe，不新增缓存服务或分页 DSL。

实现前失败方式与验收要求：

- JSON 返回稳定 id 与 detailUrl：两轮 collect、Recheck 和 Replay 始终保留同一个业务键/Record ID；没有详情到业务键映射时复查冻结父 API 请求，不能产生 URL 键替代记录。历史配置和已接受行也不能静默改变身份。
- 200 条独立详情、请求预算 100、仅一条到期：调度仅计划到期范围；更多到期项按请求预算分批。相同父 API 请求去重，返回的额外记录仍可验证，未计划项不能列为未观察。
- 排队、失败、重试与并发：调度不提前推迟业务 next_check；仅成功完成事务推进已观察范围。失败保留有界的重试机会；同一 Source 的待执行任务不重复领取，旧 generation/attempt 不覆盖新计划或当前指针。
- 1000 条 Record、每条 10 个类型化字段：真实采集及原文复算保持完整值和键，并产出可重复性能数据；JSON Pointer 不随字段数重复解析完整大响应。重复 JSON 键、非法 Pointer、false/0、1/1.0、非有限数、补充输入混淆及摘要损坏继续拒绝。
- 真实 pageNo/pageSize API：验证冻结总数、每页条数、末页及明确终止。提前空页、总数漂移、重复身份、分页超过合同或请求预算必须主动诊断；通用 JSON 示例声明单页范围，不默默冒充全量分页。

端到端工件保存实际 CLI/Worker 回执、请求账本、Run 种子与计划范围、数据库可观察
状态、导出、原文哈希、断言以及性能环境/运行命令。工件使用新目录，失败与历史
均保留。具体实现选择与执行结果在上述行为通过后补入本节。

实际实现与边界：

- `recheck.py` 单独负责目标计划、父请求证明、未观察范围与完成日期；`runs` 冻结计划，`queue` 在 Source 锁下按默认 Binding 的输出合同选择到期 Record/Document，`completion` 事务提交时推进日期。采集、领域验证和存储职责仍分离。
- `key_locator.kind=response_url` 才直接复查详情。其他业务键冻结父 GET；历史缺 parent 元数据时，只允许从该 Record 已接受 complete Result 的主 snapshot/Run inputs 恢复唯一请求，校验原文摘要。无法证明则显式 `record_recheck_request_missing`，不猜当前入口、不改旧身份。
- 自动调度按到期时间/身份排序，以不同 GET 请求为预算单位；相同父 API 的到期目标合并。Run 保存 `recheck_plan`；未计划项不计缺失，API 额外返回的有效记录不提前推进检查日期。手动 `--recheck` 保持即刻复查全部已知范围，超预算返回 `recheck_budget_exceeded`，不创建 Run、不改日期。
- 排队和失败不推进业务 `next_check`。仅 complete 中已观察的计划目标推进；未观察目标仍 unknown，并获得独立重试退避。失败退避从 30 秒指数增加、上限 1 小时；恢复清零。Source generation/run_seq/attempt fencing、待执行去重与单源 savepoint 保持有效，一个来源缺父请求不会阻塞其他来源。
- `0005_recheck_plan.sql` 只增加 Run 计划与 Record/Document 退避元数据及索引。历史字段、不可变候选与原文不回填改写；升级停止 Worker，迁移后新 pack/Binding。迁移验收冻结升级前全部列并逐值核对，新增 nullable 元数据不能导致整行形状的假失败。
- `record_validation.py` 承担类型、locator、key 与原文字节验证；`records.py` 保留持久化/版本职责。每个 Pipeline 拥有一个显式传入的 JSON LRU，至多 16 个解码对象、实际 Python 对象大小合计 64 MiB，关闭时全部释放。每条 Record 仍重新校验 snapshot/body 的内容摘要；同一 Record 的多个字段/key 共享已解析输入。超过 LRU 上限的输入只在本条验证中复用；无 hash 的独立调用不进入共享缓存。
- 通用 JSON Recipe 要求显式 `json_scope=single_page`；未声明返回 `pagination_contract_missing`。完整分页由普通 `recipes/amac_full` 承担，校验成功 envelope、页号、冻结总数、每页长度、自然键唯一性与有界终止，不增加通用分页 DSL。
