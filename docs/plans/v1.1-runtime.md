# SEAL V1.1：独立 Runtime 与三平面边界

## 1. 目标、版本与交付边界

V1.1 的主要交付是可靠 Runtime：Source 配置 → Binding → Run → Scrapy → 原文归档 → JSON → 持久化 → 执行报告。执行完成只表示满足技术契约，不表示数据准确、完整或已获发布批准。

本 Plan 是独立版本，不覆盖 [V1 Plan](v1-information-pipeline.md)、历史 ADR、Generated 或验收工件。修订决策见 [ADR-0003](../adr/0003-runtime-evaluation-management.md)，唯一派生概览见 [Generated](../generated/v1.1-runtime.html)。V1 合成验收记录仍说明 V1 的行为，不能用于证明 V1.1。

保留 Python 模块化单体、Scrapy、Procrastinate、PostgreSQL、本地内容寻址目录。不新增微服务、工作流引擎、事件总线、沙箱、评估 Schema 或插件框架。可信团队 Recipe、单组织单主机和受控 CLI 的信任前提不变。

## 2. 三个逻辑平面与依赖方向

| 平面 | 职责 | V1.1 状态 |
| --- | --- | --- |
| Runtime | 调度、采集、归档、解析、技术校验、恢复、运行数据与报告 | 本次实现 |
| Evaluation | 按候选 Binding 核对实际采集结果与原文，评估准确性、完整性、覆盖及异常，输出证据 | 必须后续建设，本次未实现 |
| Management | 管理版本、Binding、版本选择；未来消费评估证据决定审核、正式启用、发布和回滚 | 仅最小配置与默认 Binding 选择；治理未实现 |

Management 的配置指向 Runtime；Evaluation 读取 Runtime 的不可变输入和处理结果；未来 Management 消费 Evaluation 的结论。Runtime 不调用 Evaluation，不依赖审核状态。三个平面是逻辑职责，不要求拆包、拆进程或部署新服务。

Binding 保留为 Source + 不可变 RecipeVersion + 执行配置快照 + 参数的确定组合。共享 RecipeVersion 不合并 Source 的运行、配置或未来评估资格。候选不是新的运行模式：任何合法 Binding 都可执行普通 Run。

## 3. 相对 V1 的减法

| V1 能力 | V1.1 处理与原因 |
| --- | --- |
| Trial 模式、专属 namespace、CLI、审核材料生成 | 删除，不改名成预检或验证运行 |
| Gold Fixtures 比较、Trial 成功前置条件 | 删除；固定样本通过率不能代替总体质量评估 |
| Review、Activation、rollback、withdraw、发布事件写入 | 删除当前执行链和 CLI；历史数据只读保留 |
| Source `needs_repair` 审核闭锁 | 不再读取或写入；失败后可直接新建普通 Run |
| `expected_urls`、覆盖率结论、产量跌幅门禁 | 删除配置和运行逻辑；独立预期只属于工程验收 |
| 发布 JSON | 改为运行数据导出，显式 `quality_status=not_evaluated`；这是一项破坏性出口变更 |

| Schema、输入血缘、字段 locator、下载/解析错误 | 保留为技术契约；不证明字段业务含义或总体完整性 |

## 4. 当前配置、数据与接口合同

### 4.1 配置和最小版本管理

`source apply` 保存公开来源配置；`archive_approved` 只表示操作者已确认存档许可，不是解析结果审核。访问范围、预算、身份、输出 Schema 和参数随 Binding 固定。调度间隔、暂停和冷却是 Source 的操作配置。未知配置字段与重复 YAML 键仍拒绝。

`source select SOURCE --binding ID --expect-generation N` 选择周期调度和省略 `--binding` 时的默认版本，核对 Source 归属及运行环境，CAS 递增 generation 并解除暂停。不要求任何 Run 成功或人工审核。选回旧 Binding 也是同一操作，没有正式发布或回滚工作流。

`run SOURCE --binding ID` 与 `run SOURCE` 调用同一个 `create_run` / `execute_run`。显式 Binding 不必等于默认 Binding，但不能跨 Source。`--enqueue` 使用同一持久队列；`--recheck` 从已知文档生成详情种子。模式只有 `collect`、`recheck`、`replay`。

### 4.2 保留模型

| 模型/物理表 | V1.1 语义 |
| --- | --- |
| Source / `seal_source` | 配置、可空默认 Binding、操作代次、序号、暂停、冷却、调度游标 |
| RecipeVersion / `seal_recipe_version` | 不可变源码、helper、资源、依赖锁和执行环境清单 |
| Binding / `seal_binding` | 不可变 SourceConfig、参数、RecipeVersion 与 fingerprint |
| Run / `seal_run` | 固定 Binding、模式、代次、顺序、attempt、deadline、job、输入、结果、错误和报告 |
| Observation / `seal_fetch_observation` | 每次实际网络交换；失败没有伪造 body；Replay 不新增网络观察 |
| Document / `seal_document` | Source 内 URL 身份及最近技术接纳的 Observation/Revision，不代表质量确认 |
| Revision / `seal_revision` | 顺序正文变化；A→B→A 三次修订，共用两份 body |
| ProcessingResult / `seal_result` | 输入清单 + Binding 的处理键与不可变 JSON；同键异值明确报错 |
| 操作/历史审计 / `seal_decision` | 新代码只写 control；V1 审核、发布、撤回记录保留可查 |

RawSnapshot 与 body 继续内容寻址。相同内容每次获取仍有独立 Observation；同文换 Binding 新增 Result，不新增正文 Revision。在线 Run 共享 Source 的 `runtime` 文档空间；Replay 使用各 Run 的独立空间，不推进在线状态。

`report.outputs` 在完成事务中固定 Result、Revision 和 Observation 的关联，包括 partial 的有效暂存结果。后续重复获取不能改变某 Run 的输入血缘。报告包含 result_count、错误、Stats 和 `quality_status=not_evaluated`，没有质量评分或覆盖率。

`export SOURCE --run ID` 导出指定 Run 的可用结果及其技术状态，包括 partial；跨 Source 拒绝。默认 `export SOURCE` 汇总每个文档最近成功在线 Run 的结果，不读取 V1 发布指针，不过滤候选 Binding。失败的新 Run 不覆盖上一次成功结果；导出显示 stale/最新执行状态。这是便利的运行视图，不是权威业务数据集。历史 V1 结果通过 inspect 查询，再用新 Binding Replay；不把旧发布数据自动标记为 V1.1 已执行。

### 4.3 技术校验与空集

保留 Schema、非空 title/body、日期格式、locator 与原文一致、主资源 URL/方法/状态、Supplementary 输入归属、对象摘要、实际请求链与已声明文档引用的完成检查。它们只验证 Recipe 的输入输出契约。

Locator 保留现有 `xpath/text/json/pdf/segments` 定位结构，不保存脱离原文的替代值。可选 `transform: date_iso` 将完整的 `YYYY-MM-DD` 或 `YYYY年MM月DD日` 片段经日历校验转换为 ISO；不接受任意格式串、代码或未知转换。`segments` 可加 `separator`，默认仍为单换行，只允许最长 8 个字符的空白及 `:：,，;；/|·—-` 分隔标点。每个子片段从同一原文独立定位，显式拼接不允许空片段，也不允许子片段悄悄切换 snapshot。转换、拼接后仍逐字段严格比较最终输出；错误定位或错误输出不能形成有效 Result。原始 locator（含转换和分隔符）保存在 Result，Replay 使用相同校验逻辑。

没有新 Schema 或数据迁移，旧 locator 不带转换时保持原行为；历史 Binding、Result 和原文不重写。旧 Recipe 源码可重新 pack 使用，跨引擎环境仍遵守已有摘要检查：重新 pack/create Binding 后可重放旧输入，不能把放开环境漂移当作兼容性修复。

状态继续使用现有结构：`complete` 表示技术执行完成（允许零结果），`partial` 表示存在技术错误但保留已通过校验的结果，`quality_status=not_evaluated` 表示未经过独立 Evaluation。报告、指定 Run 的导出及每份文档的 `run_status` 一致传递；默认成功视图不以 partial 覆盖历史成功结果。

不比较外部预期集合、不推断漏采比例、不检查总体质量。成功完成但没有结果的 Recipe 可返回零结果报告。Recipe 自身遇到无法解析的模板仍可明确报错；这不是 Runtime 质量评估。

## 5. 实际模块和执行流程

`cli` → `configuration/recipes` 保存配置和版本；`cli/queue` → `runs` 管生命周期；`crawl` 组装原生 Scrapy；`archive` 归档；`items` 保存修订与 JSON；`completion` 形成技术报告；`export` 读取运行数据；`db/core` 提供事务、fencing 和内容寻址。

1. 创建 Run，固定 Binding、generation、Source 内 run_seq、种子与期限；入队与业务行同事务提交。
2. 开始 attempt，递增 epoch，检查暂停、冷却和 Source 写入序号。
3. 启动 RecipeVersion 记录的 Python 子进程并验证环境摘要，不原位替换依赖。
4. 固定 `ROBOTSTXT_OBEY=False`，不创建自动 robots 辅助请求。历史配置中的 `robots` 只为外部快照兼容保留，不影响执行；移除 robots 路径豁免及完成状态特判，显式业务 URL 仍接受正常范围与 HTTP 错误检查。Scrapy 使用原生下载、重试和跳转。响应顺序保持 HttpCompression(610) → Archive(605) → Redirect(600) → MetaRefresh(580) → Retry(550)。
5. body 与清单落盘并验证，Observation 提交后才进入 callback；失败阻止解析该响应。
6. Item Pipeline 验证技术契约和输入血缘，同事务保存 Revision、Result 和 Run 引用。
7. Crawl 关闭后完成事务验证对象、请求链和 fencing，保存报告及不可变输入对应关系；不生成发布事件。
8. CLI 导出可复算原文引用、来源 URL、JSON、Binding、RecipeVersion、Run、Observation、Revision 和执行状态。

## 6. 并发、恢复和执行安全

所有在线 Binding 共用 Source 的 run_seq/write_seq 与 generation，显式候选不绕过 fencing。新 Run 开始后，旧 Run 不能抢回写资格；同 Run 新 attempt 使旧 epoch 失效。选择默认 Binding或暂停递增操作代次，使在途旧代次失效。不以 Binding 是否为默认值作为提交条件。

请求继续受域名、路径、方法和预算约束；非公网 IP 字面量以及 localhost/local/internal 名称拒绝，只有隔离验收进程显式设置 `SEAL_ALLOW_LOOPBACK=1` 时可访问 loopback。这是基本地址限制，不承诺 DNS 重绑定防护或恶意 Python 隔离。

锁顺序仍是 Source → Run → Document。过期响应可留 Observation，但不得推进文档当前状态。Replay 只约束自身 epoch/deadline。Procrastinate 负责整 Crawl 的持久任务、执行锁、周期及 stalled 恢复；Scrapy 负责一次 Crawl 内请求重试。最多三次 attempts，总 deadline 不重置；确定性错误结束为 partial，临时故障有限重跑。失败不设置人工审核闭锁。

完成事务重入返回已存结果，job 确认前崩溃不重复采集；body/DB 无跨系统 exactly-once，孤儿对象暂保留。归档不可读/损坏时导出明确 unavailable。普通子进程、Scrapy 配置和可信代码约定不是恶意 Python 沙箱；Agent 的未来写权限仍只限 Recipe，安全准入与质量评估须分开设计。

## 7. 增量迁移与升级/回退

保留已应用的 `src/seal/schema.sql` 原样，新增 `src/seal/migrations/0002_runtime.sql`。迁移表记录版本和摘要；重复 migrate 不重放迁移，历史迁移摘要漂移拒绝。事务锁串行化业务迁移。

迁移保留所有历史 Run、Trial、Review、Gold 审核 payload、Revision、Result、原文引用和发布指针字段。不迁移出大型评估 Schema。新增模式约束使用 NOT VALID，允许旧行留存，但新插入只能用当前模式；已有终态旧 Run 只读，不可重试。旧的未结束任务终止并附迁移诊断，Procrastinate 后续只确认存储的终态，不执行旧 Trial。

迁移前停止 CLI 写入与全部 Worker，备份数据库和原文目录。旧 Source 自动暂停、递增 generation，并以 control 审计保存迁移前配置；从 Source 当前配置移除 `expected_urls`。历史 Binding 快照不改。在线 Document 的 namespace 从 production 改为 runtime，ID 与 Revision 链不变；历史 Run 的 mode/namespace 不改。其他历史治理列保留为只读遗留数据，新代码不使用它们。

旧 RecipeVersion 包含 V1 引擎摘要，不能冒充在 V1.1 环境复现。升级后重新 pack、create Binding，再普通 Run/Replay，必要时 source select。原文归档合同版本不变，旧 Run inputs 可供新 Binding 重放。严格复现旧代码需配套保留旧 checkout/venv 和升级前数据库副本；不要让旧 Worker 连接升级后数据库。回退恢复配套备份，不提供破坏性 down migration。

## 8. 先验失败方式与验收合同

编码前固定以下可观察行为，优先修改已有 E2E，不补结构性单元测试：

| 场景/失败方式 | 外部断言 |
| --- | --- |
| 无默认 Binding、无任何审核记录 | 候选普通 Run 完整保存原文/JSON/版本；执行不会设置默认 Binding |
| 默认与候选不同、共享 Recipe 的 A/B | 同路径运行；跨 Source Binding 拒绝；A 新版本不改变 B；同文新 Binding 只增 Result |
| Trial/Review/Activation/withdraw 入口或旧模式复活 | CLI 拒绝；数据库拒绝新 Trial；旧 Trial 可 inspect/Replay，但不可 retry |
| 以技术成功冒充质量通过 | 报告和导出明确 not_evaluated；无 coverage/Gold/发布审批字段 |
| 空结果、解析失败、部分结果 | 零结果可以技术完成；partial 原文和有效 JSON 可按 Run 查询；无 needs_repair 审核闭锁 |
| body/DB 故障、压缩跳转重试、敏感输入 | 复用 M0 的归档前置、诊断和禁止敏感信息持久化断言 |
| Replay 缺失/多义、源站关闭 | 明确失败或一致 JSON；请求账本证明零网络，不下载补齐 |
| A→A→B→A、同键异值、环境漂移 | 观察不丢；三次修订两份 body；异值不覆盖；引擎/包漂移拒绝 |
| Worker 在 body、Result、完成提交后崩溃 | 真实 Worker 有界恢复；无悬空引用；完成重入不重新下载 |
| 旧 attempt/Run/generation 晚到 | 不能覆盖新状态；候选也受同一 fencing |
| V1 数据升级与重复迁移 | 历史不可变行与归档摘要不变；旧任务不执行；新普通 Run 和旧输入 Replay 均可运行 |
