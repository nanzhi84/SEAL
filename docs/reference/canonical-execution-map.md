# Canonical Execution Map Specification (CEMS)

**Version:** 1.1  
**Document Type:** Engineering Documentation Standard

## 1. 定义与目标

Canonical Execution Map（CEM）是一种面向源码的层级化执行图规范，用于描述软件系统从入口到终态的完整执行过程。

CEM 结合函数调用树、执行流程、状态机、并发关系和数据操作，以纯文本树状结构为主要表现形式。

CEM 是工程文档约定，不属于 UML 官方标准。

必须遵循以下原则：

1. **Single Map**：使用一张主图覆盖完整执行链路，避免将同一流程拆散到多个独立图中。
2. **Source Fidelity**：所有函数、调用关系、执行顺序和状态变化必须有源码依据。
3. **Information Preservation**：保留影响系统行为与正确性的关键细节，不得为缩短篇幅而删除重要机制。
4. **Hierarchical Readability**：通过阶段、模块、函数和行为细节构建清晰层级。
5. **Explicit Semantics**：明确区分函数调用、条件判断、状态变化、副作用、并发与异常路径。
6. **Maintainability**：使用纯文本格式，支持 Git Diff、代码审查、全文搜索与自动生成。

## 2. 文档结构

CEM 正文不使用标题、项目名称、版本号、元信息或装饰性横幅，直接从第一个执行阶段开始。

标准结构：

```text
[0] ENTRY & DISPATCH
...

[1] PREPARE
...

[2] EXECUTE
...

[3] FINISH
...
```

阶段名称由实际系统决定，不强制所有项目采用相同阶段。

结构要求：

1. 阶段统一使用 `[N] NAME`，可附加简短说明。
2. 阶段编号从 0 开始，按主要执行顺序递增。
3. 每个阶段从最左侧重新开始缩进。
4. 阶段之间仅使用一个空行分隔。
5. 跨阶段关系使用 `进入阶段 [N]`。
6. 不重复展开已在其他阶段定义的完整执行过程。
7. 不使用分隔横线、ASCII 装饰框或其他无实际语义的元素。
8. 不强制在正文记录版本、Commit SHA 或核验状态，这些信息可以由文件名、Git 历史或外部文档管理。

## 3. 层级规则

CEM 采用四级语义层级。

| 层级 | 内容 | 示例 |
|---|---|---|
| L0 | 执行阶段 | `[2] EXECUTE` |
| L1 | 主要模块或入口 | `runs.py: execute_run()` |
| L2 | 函数调用与控制结构 | `_execute_attempt()`、`[PARALLEL]` |
| L3 | 具体行为与副作用 | SQL、状态变化、校验、文件操作 |

允许根据源码复杂度增加嵌套深度，但不得为了视觉整齐而改变真实调用关系。

树状结构统一使用：

```text
├── 子节点
│   ├── 子节点
│   └── 子节点
└── 最后一个子节点
```

同一父节点下，原则上按照真实执行顺序排列子节点。若执行顺序不确定或存在并发，应明确标注，不得暗示严格先后。

阶段之间必须重置缩进，避免整张图随着执行深度不断向右延伸。

## 4. 节点语义标记

统一使用以下语义标记。

| 标记 | 定义 |
|---|---|
| `[DB]` | 数据库读写、事务及锁操作 |
| `[IO]` | 文件、网络及外部资源操作 |
| `[CHECK]` | 校验、条件判断及安全检查 |
| `[STATE]` | 状态转换及状态持久化 |
| `[CONFIG]` | 运行参数及环境配置 |
| `[SPAWN]` | 创建进程、线程或执行单元 |
| `[ASYNC]` | 异步任务派发 |
| `[PARALLEL]` | 并发执行区域 |
| `[JOIN]` | 并发执行的同步或汇合点 |
| `[LOOP]` | 循环执行 |
| `[RETRY]` | 重试机制或重试决策 |
| `[CLEANUP]` | 资源释放及清理 |
| `[RETURN]` | 返回值、回执及退出 |
| `[ERROR]` | 错误处理及异常路径 |
| `[UNVERIFIED]` | 尚未通过源码确认的描述 |

使用规则：

1. 标记必须表达明确语义。
2. 同一节点允许组合标记，如 `[CHECK/DB]`。
3. 普通函数调用直接使用真实函数名，无须添加额外标记。
4. 标记不能代替函数名、操作对象或实际行为。
5. 不为普通描述随意创造新标记。
6. 新增标记必须具有明确且不可由现有标记表达的语义。
7. 语义标记不要求每行都出现，只标记需要特别区分的行为。

## 5. 函数与调用关系

函数统一使用：

```text
module.py: function(arg1, arg2)
```

要求：

1. 保留实际文件名和函数名。
2. 参数只保留理解调用所必需的部分。
3. 父子结构必须对应真实调用关系或明确的控制结构。
4. 不得将函数返回后由上层触发的操作错误表示为该函数的子调用。
5. 框架回调、事件触发、进程入口必须与直接函数调用区分。
6. 同一函数在多个位置出现时，可以使用阶段引用避免重复展开。
7. 不得根据函数名称推断未经确认的调用关系。

函数执行产生的关键副作用应作为子节点记录。

```text
runs.py: begin_attempt()
├── [DB] 递增 attempt_epoch
└── [STATE] pending → running
```

必须区分以下关系：

- **Call**：直接函数调用。
- **Dispatch**：任务或事件派发。
- **Callback**：框架或事件系统回调。
- **Spawn**：新执行单元启动。
- **Return**：执行结果返回。
- **Transition**：状态或执行阶段转换。

普通树枝默认表示层级归属。涉及其他关系时，必须通过标记或文字明确其含义。

## 6. 控制流表达

### 6.1 条件分支

使用明确的条件和分支结果。

```text
[CHECK] status
├── complete  → accept_documents()
├── retryable → retry decision
└── failed    → failed handling
```

要求：

1. 条件必须与实际代码逻辑一致。
2. 保留影响主流程的关键分支。
3. 分支应尽量互斥，并覆盖实际可能的结果。
4. 不得将推测性的异常路径描述为已实现行为。
5. 分支后的汇合或返回应明确表达。

### 6.2 循环与重试

使用 `[LOOP]` 表示循环作用域，使用 `[RETRY]` 表示重试条件和决策。

```text
[LOOP] Attempt
├── begin_attempt()
├── execute attempt
└── [RETRY] Result
    ├── retryable → next attempt
    └── terminal  → exit loop
```

必须区分：

- Attempt Result：单次尝试的结果。
- Run Status：持久化任务状态。
- Terminal Status：任务最终状态。
- Retry Policy：重试条件、次数和退避策略。

存在代际机制时，必须保留 `attempt_epoch` 等关键字段及其更新位置。

### 6.3 并发执行

使用 `[PARALLEL]` 明确表达多个执行单元。

```text
[PARALLEL]
├── [A] CHILD: Worker Process
│   └── execute task
└── [B] PARENT: Supervisor
    └── monitor process

[JOIN] Process completion
```

必须明确：

1. 并发执行单元的身份。
2. 各执行单元的主要职责。
3. 进程、线程或任务之间的通信方式。
4. 同步、退出或汇合条件。
5. 异常退出后的处理路径。
6. 必要的资源清理行为。

`[JOIN]` 仅在存在实际同步或控制流汇合时使用，不得暗示所有并发分支均正常完成。

### 6.4 异步任务

异步任务派发必须明确生产者、任务载体和消费者。

```text
queue.py: enqueue(run_id)
├── [DB] defer_job() 原子入队
├── [RETURN] pending receipt
└── [ASYNC] Worker
    └── crawl_job(run_id) → 进入阶段 [2]
```

如果任务入队与数据库写入共享事务，必须保留其原子性语义。

### 6.5 资源清理

资源清理使用 `[CLEANUP]`，并说明触发条件。

```text
[CLEANUP] finally
└── 若子进程仍存活
    ├── SIGTERM
    └── 等待超时 → SIGKILL
```

不得将条件性清理描述为无条件执行。

## 7. 数据与状态表达

### 7.1 数据库操作

数据库操作必须标明操作类型和目标。

```text
[DB] INSERT INTO seal.run
[DB] UPDATE seal.document.latest_document_version
[DB] SELECT run + binding
```

对于关键事务，必须说明：

- 原子性边界。
- 锁类型及保护范围。
- 并发冲突处理。
- 提交前置条件。
- 必要的回滚或失败处理。

不要求展开完整 SQL，但不得省略影响正确性的关键约束。

### 7.2 状态转换

状态变化使用：

```text
[STATE] pending → running
[STATE] running → finishing
[STATE] finishing → complete
```

必须区分：

1. 内存中的临时状态。
2. 数据库中的持久化状态。
3. 函数返回的决策结果。
4. 系统对外暴露的最终状态。

不得将临时决策结果错误标记为数据库终态。

### 7.3 数据身份与版本

存在数据身份、版本控制或去重机制时，应保留：

- Identity 的生成或解析方式。
- Version 的创建条件。
- Fingerprint 或 Processing Key 的计算位置。
- 去重及冲突检测。
- 最新版本指针的推进条件。
- 数据来源与处理血缘。

不得将暂存、审计和正式接受混为同一个操作。

## 8. 信息保留规则

以下内容属于关键执行信息，原则上必须保留：

1. 主要执行入口与真实函数调用关系。
2. 进程、线程、任务队列及并发边界。
3. 数据库事务、锁、代际栅栏及原子提交。
4. 重要状态转换与失败重试机制。
5. 数据身份、版本、去重与血缘关系。
6. 安全、权限、作用域及完整性校验。
7. 影响执行结果的配置和参数。
8. 异常处理、资源回收及最终返回。
9. 外部框架的关键回调与执行顺序。
10. 跨模块的数据传递与持久化副作用。

允许压缩：

- 与执行语义无关的实现细节。
- 重复出现的相同流程。
- 可从函数名直接理解的简单操作。
- 不影响控制流的辅助日志与格式化行为。
- 对主执行链路没有影响的内部辅助函数。

**信息压缩不得改变执行语义、调用归属、状态转换或事务边界。**

## 9. 排版规则

CEM 采用纯文本代码块，使用等宽字体，不依赖 Mermaid、Graphviz 或其他图形渲染工具。

统一约定：

| 符号 | 用途 |
|---|---|
| `├──` | 非末尾子节点 |
| `└──` | 最后一个子节点 |
| `│` | 父级结构延续 |
| `──►` | 执行方向、触发或阶段跳转 |
| `→` | 简短状态变化或数据转换 |
| `:` | 节点说明 |
| `()` | 函数调用 |
| `[]` | 阶段编号、语义标记或分支标签 |

每个节点优先采用：

```text
函数或操作 ──► [语义] 关键行为
```

排版要求：

1. 正文直接从 `[0]` 开始，不使用文档标题。
2. 阶段之间只使用空行。
3. 每个阶段独立缩进。
4. 长描述拆成子节点。
5. 同级节点使用一致的缩进宽度。
6. 不强制所有行等宽。
7. 不使用大面积装饰性边框。
8. 不为了对齐而增加无意义的空格。
9. 保持函数名、表名、字段名和状态值可直接搜索。
10. 中文用于解释业务语义，代码标识符保留源码原名。

## 10. 正确性与维护规则

CEM 必须以明确的代码版本为依据，但版本信息无须写入执行图正文。

维护要求：

1. 函数名称、调用关系和状态机必须与源码一致。
2. 新增关键执行分支时同步更新。
3. 删除函数或模块时移除失效节点。
4. 重构后重新检查阶段引用与控制流汇合。
5. 无法确认的行为标注 `[UNVERIFIED]`。
6. 不得仅根据旧文档推断当前实现。
7. 不得为了匹配已有执行图而忽略源码中的实际差异。
8. 发现文档与源码不一致时，以源码为准，并更新执行图。
9. 关键执行路径变更应与相关代码变更一同提交。
10. 不要求每次代码变更都重绘整张图，只更新受影响的节点及其关联路径。

建议在代码审查中检查执行图是否需要同步更新。

## 11. 验收标准

一份 CEM 只有满足以下条件才能被视为 Canonical：

- [ ] 正文直接从执行阶段开始，无标题和装饰性横幅。
- [ ] 从入口到终态的主执行路径完整。
- [ ] 关键函数与模块名称准确。
- [ ] 函数调用与控制流关系没有混淆。
- [ ] 并发、异步与同步边界明确。
- [ ] 数据库操作与状态转换准确。
- [ ] 失败、重试和资源清理路径完整。
- [ ] 关键安全及完整性机制未遗漏。
- [ ] 阶段引用能够正确连接执行路径。
- [ ] 文档与指定源码版本一致。
- [ ] 无未经标记的推测性实现描述。
- [ ] 关键数据身份、版本和事务边界得到保留。
- [ ] 信息压缩未改变实际执行语义。

## 12. 优先级原则

当规范之间发生冲突时，按以下顺序处理：

**Correctness > Completeness > Readability > Brevity > Visual Consistency**

即：

1. **Correctness**：准确性最高优先级。任何内容不得违背源码。
2. **Completeness**：完整保留影响系统行为和正确性的关键机制。
3. **Readability**：通过层级和语义标记提高可读性。
4. **Brevity**：在不损失信息的前提下减少冗余。
5. **Visual Consistency**：视觉统一服从实际执行结构。

允许文档较长，允许节点深度不均匀，但不得为了美观、简洁或形式统一而改变实际执行逻辑。
