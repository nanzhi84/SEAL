A

先理解：一个 Source 应该有多大？

把 Source 定义成一个稳定的内容渠道

例如“海口市监处罚公告栏目”，而不是整个政府网站。 同一网站可以同时提供静态公告、公开接口和登录查询。 它们需要不同的采集规则。

Source 回答“采什么”。Recipe 回答“怎么采”。 Binding 固定这次使用的版本和参数。 适配主要修改配置和 Recipe，复用现有 Runtime。

这三个栏目采集时无需用户输入企业名称。 页面上的站内搜索框不影响直接获取公告。

  1. 只选择目标栏目的详情链接。
  2. 分别定位标题、日期和正文。
  3. 按真实分页规则请求下一页。

哪些来源先放后面？

情况 当前障碍 首版处理
登录、验证码或身份查询 需要用户状态或业务材料 保留人工入口，单独评估
HTTP 错误或连接失败 本轮无法确认页面机制 显示未知，不猜测输入字段
明确 robots 禁止 未继续采集被禁止的路径 不纳入自动采集范围
PDF、附件或图片正文 下载成功不代表正文可提取 标明附件状态，逐源核对
只有首页和导航 尚未找到目标业务数据 先找栏目，再写 Recipe

政府采购合同的默认列表可读，详情本轮超时。 它的筛选表单含验证码，不能由默认列表推断筛选可用。 深圳某 PDF 补测返回 HTTP 200，正文提取仍未验收。

失败和未命中必须保留语义

取不到页面，表示“采集失败”。 搜索没有结果，表示“已采集范围内未找到”。 两者都不能解释成“该企业无风险”。

首批来源建议按什么顺序适配？

  1. 第一步海口单源采集两页和详情；按公司关键词检索并回看原文
  2. 第二步最高法与最高检验证长正文和不同分页规则能复用执行流程
  3. 第三步基金公开名录适配嵌套 JSON；验证完整分页与记录去重
  4. 第四步其他查询渠道按业务价值处理动态接口、身份与访问条件

第一步就能形成可演示的产品流程。 不必等待所有网站适配完成。

接入完成的标准： 用户能找到已知样本，并核对原文。 重复采集不制造重复内容，内容变化留下修订。 失败项、采集时间和覆盖范围始终可见。
