查看四重指纹与不可变提交语义

version_fingerprint = digest(input_fingerprint + parser_fingerprint)。parser_fingerprint 涵盖 Adapter、Office/TCVN3 提取器、PDF 扫描检测、OCR 引擎（tesseract / br-ocr-v1）与 quality_check 规则。与当前 Version 比较，A→B→A 保留三次演进。

content_hash 比较规范业务内容；共享批量原件的全量哈希和定位属于血缘，不能让无变化的单篇文档误升版。同轮 delivery_key 重放须同时核对输入、解析器与内容三指纹，禁止原地改写已提交 inputs_ref。

16 列文件交付：严格对齐《法规案例元数据上传模板》

固定目录与重命名规则

delivery/
├── metadata.xlsx
├── markdown/
│   └── <资料名称>_<文件哈希前8位>[_<序号>].md
├── originals/
│   └── <资料名称>_<文件哈希前8位>[_<序号>].<ext>
└── manifest.json

metadata.xlsx 中的 解析后文件 与 原始文件 列精确对应 markdown/ 与 originals/ 下的文件名；所有 64 位哈希均可直接用于 GET /files/{sha256}。

16 列结构与三类拆分规则

16 列固定表头：资料名称、解析后文件、资料类型、文件哈希、采集时间、原始文件、文件顺序、文号/案号、发布机构、发布日期、生效日期、失效日期、状态、来源名称、来源详情页、来源记录号。

  • 单文件资料：1 行，文件顺序 留空。
  • 同一资料连续分卷：拆分为多行，重复填写相同的 资料名称 与 来源记录号，文件顺序 依次填 1、2…；顺序不明时阻止装配。
  • 同来源下独立附件：拆分为独立行，填写各自 资料名称，文件顺序 留空，共享 来源记录号。

内容完整

每行恰有一个非空 .md；有原件时 文件哈希 为原件 SHA-256，无独立原件时为 .md SHA-256。必需附件缺失或未过 quality_check 不形成成功版本。

结果可复现

.md 字节在 Version 提交时写入 CAS。导出器只读固定 Snapshot，冻结排序与工作簿属性，重复导出载荷一致。

manifest 对账

manifest.json（seal.delivery.v1）记录每行对应的 resource_id、version_id、markdown_hash、文件哈希、locator 及覆盖摘要。

验收面向最终可见结果

对应与完整性

  • 16 列 metadata.xlsx、markdown/、originals/、manifest.json 与 GET /results、GET /files/{sha256} 全量对账。
  • 单文件、连续分卷（文件顺序 = 1, 2...）与同源独立附件拆分准确，顺序不明阻止装配。
  • Office 伪装容器、TCVN3 混合编码、混合扫描 PDF 与双引擎 OCR 质量门禁全部可验证。
  • 搬移包并断网执行 seal export verify，相对路径与 SHA-256 全部通过。

状态与故障行为

  • 旧 /sources、/attachments/{id} 彻底移除；未授权或非已发布快照的 SHA-256 请求一律返回 404。
  • 批量提交一半退出，接管后补齐，失效 attempt 无法继续写入。
  • 列表重排不制造假版本；解析器/OCR 升级支持零网络离线重解析。
  • 缺件、损坏、取消、超限不生成完整交付目录。
