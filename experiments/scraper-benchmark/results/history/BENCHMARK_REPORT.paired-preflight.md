> 当前结论：**没有有效的 Scrapy vs Firecrawl 实时配对实验，不能据此选择主框架。**
> 已撤回上一版“暂以 Scrapy 为优先基线”的比较性建议。历史能力验证和费用记录仍保留，但不用于框架排名。
> 本次只完成协议冻结和离线审计，**没有重新运行目标网站采集，也没有新增 Firecrawl 调用或 credits**。

## 1. 为什么上一轮不能比较

| 问题 | 后果 | 本次修正 |
|---|---|---|
| Scrapy 抓真实网站，Firecrawl 上传合成 HTML | URL、网络链路、输入内容和功能都不同 | 两者只消费 `paired_protocol.json` 中同一个真实 URL 清单 |
| Scrapy 旧网络结果对比后来的 Firecrawl 结果 | 时间、页面版本、缓存等未控制 | 必须在同一新轮次配对运行；禁止用历史结果填格 |

### 两个场景不能混用

1. **最少代码拿内容**：Scrapy + trafilatura/pypdf 对比官方 Firecrawl Scrape 的原生清洗/解析能力。输出归一到相同字段与纯文本含义；只转换表示，不总结、不补写缺失字段。原生 Markdown/HTML 均保留。
2. **固定 Recipe 的长期采集**：两方获取的 raw 内容进入**同一个固定版本 Python Recipe**，用同一校验器和 oracle。这里比较的是获取/原件可用性，不把共享 Recipe 的提取能力算成某个框架的优势。

Scrapy + Playwright 若启用，是同一个 E 目标和相同可见结果的**独立第三组**。不把它的成功混入基础 Scrapy，也不拿本地 JS Fixture 代替真实 E。

## 3. 实验变量与比较资格

### 必须一致

- 同一 `campaign_id + case_id + url + function_id + scenario + oracle_sha256`。
- 同一目标文档集合、字段定义、正文完整性标准、附件范围和每来源 5 份详情上限。
- 同一新轮次；每个配对开始间隔不超过 300 秒。按 case 交替先运行哪个引擎，降低顺序偏差。
- Scrapy 关闭 HTTP cache；Firecrawl 设置 `max_age=0`、`store_in_cache=false`。缓存命中不得纳入实时比较。
- 固定声明的 UA/语言，在服务支持的范围内一致；SDK 与客户端重试为 0。
- 不跟随未经审批的隐式重定向，不因失败换 UA、代理或引擎；遇 401/403/412/429 同源停止并保留双边状态。
- 双方用同一份独立标注，不以两者彼此输出或 HTTP 200 作为正确答案。
- 配对原件若显示来源内容变化，标 `SOURCE_CHANGED_OR_UNKNOWN`，不强行算准确率或耗时优势。

### 必须显式承认没有控制的变量

Firecrawl Cloud 与本地 Scrapy 的出口、服务端渲染基础设施和内部请求过程不同。即使 URL 一样，也不能保证服务器返回相同版本或相同地域页面。因此：

- 可以评估各自**端到端部署方案**对同一任务的有效结果与成本。
- 不能直接解释为框架内核的速度优劣。
- 如果没有足够原件或独立标注确认相同内容，相关指标为 UNKNOWN，不排胜负。
- 同一页面/同一功能不要求内部 API 次数完全相同。若 Firecrawl 额外取 PDF 原件，应计入其完成相同业务合同的总成本，而不是给 Scrapy 人为添加无用请求。

## 4. 新预算与当前执行阻断

拟定新轮次上限仍为 **80 次请求 / 30 credits，仅免费额度**。这是协议中的待确认预算，不是已经花费或已经获得新额度的证明。

不含后续独立标注、robots 重定向或人工导航的主队列预计：

- Scrapy：16 个源页面 GET。
- 双方共用政策检查：6 个源域 robots 初次 GET。
- Firecrawl：16 个对应 URL 的 Scrape，加 1 次 PDF 原件读取（若原生解析不同时返回原件）。
- 前后额度查询：2 次。
- 合计 **41 次客户端可见 HTTP/API 请求**；预留 **22 credits**。若政策跟进或格式费用超预算，停止，不能扩张范围。

**关键未确认项：80 次是否允许按客户端可见 HTTP/API 请求计算？**

当前官方文档表明 Crawl 的 `delay` / `maxConcurrency` 控制的是页面 scrape 间隔和并发；没有找到足以验证云端所有源站 HTTP 子请求、重定向和资源请求的硬限额/逐请求证据。不能把“1 次 Scrape API”谎报成“1 次源站 HTTP 请求”。

因此保留两条选择：

1. **云端端到端对照**：确认新一轮按客户端 HTTP/API 请求限额，页面任务串行且间隔至少 3 秒；云端源站内部请求量和内部子请求限速记 UNKNOWN，不声称满足严格逐源站请求硬限额。仍不允许绕过任何访问限制。
2. **严格源站请求控制**：继续坚持所有源站请求都可计量、每域并发 1/间隔至少 3 秒，那么需要具有可观测并可限流出口的自托管 Firecrawl。仅设置客户端 delay 或 JSON 中的一个布尔值不构成此控制。

本地已检查运行容器，没有发现可识别的 Firecrawl 服务；未启动或修改任何现有服务。历史那轮 6 次合成 Parse 授权已用完，不能用它覆盖本轮真实网站任务。

## 6. 当前能回答和不能回答的选型问题

1. **Firecrawl 能否替代 Scrapy？** 目前没有有效配对证据，不能作出替代或不可替代结论。
2. **Firecrawl 仍需哪些 SEAL 业务能力？** 原件持久化、身份、字段校验/证据、Revision、调度完整性、发布策略和 Agent 隔离仍需业务层；这不是对照实验得出的优劣排名。
3. **Scrapy 的额外成本？** 逐源 Recipe、异构解析和必要浏览器集成是可见工作项；相较 Firecrawl 多多少代码或工时，尚未同功能实测。
4. **混合是否值得？** 目前无实测边际收益，既不能宣称值得，也不能证明没有收益。不得用受限来源做换引擎兜底。
5. **哪个适合 Agent 修复？** 旧合成结果说明双方原件都可能进入相同 Python Recipe；不能将 Agent 修复说成 Scrapy 独占优势。真实网站修复成本和安全边界仍待验证。
